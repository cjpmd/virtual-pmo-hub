# Governance and decisions: audit (Stage D0, 14/10/2026)

Read-only audit before building decisions and governance routing (stages D1–D3). Sources: the
live Supabase project (`xvdlmtkzfmbcegkmampz`, demo organisation "University of Dundee"), the
repo at `main` (`109cbb3`), `docs/schema.md`, `docs/data-layer.md` and
`docs/financials-and-business-cases.md`. Nothing was changed.

## Summary

- **The schema for a decision log already exists and is seeded.** There are 16 decisions in
  the demo organisation, with options, actions and links. It covers almost every D1 field.
- **The app reads it live** (no mock data, no browser storage), but **nothing can create a
  decision**. The only insert is "Supersede". Two screens show a toast pointing to a create
  path that doesn't exist.
- **Forums are labels in a lookup list** (`lookup_values`, `decision_forum`). There is no forum
  table, no meetings, no agenda, no minutes, no chair and no members.
- **"Committee" is a separate idea**: Governance-type collections plus `committee_packs` (built,
  never issued, 0 rows). Nothing joins a committee to a forum.
- **The approval of a business case was designed as a decision.** The column
  `business_case_versions.decision_id` references `decisions`. A specified RPC,
  `decide_business_case`, was never built, so no business case can be approved today.
- **Gate approvals aren't stored anywhere.** Status reports never write `decisions_needed`.

## 1. Decisions

### Tables (all exist, RLS on, tenant guard, audited)

- **`decisions`** (16 rows, demo org):
  - Identity and scope: id, ref, tenant columns, and scope (`portfolio_id` / `programme_id` /
    `project_id`, exactly one).
  - Content: title, context, `chosen_option_id`, rationale, `decision_maker_id` (→
    `resources`), `forum_id` (→ `lookup_values`, list `decision_forum`), `needed_by_date`,
    `decision_date`, `status`.
  - Impact: `impact_scope`, `impact_cost`, `impact_time` and `impact_benefits`, each a bool with
    a `_note`.
  - Record keeping: `evidence_link`, `supersedes_id` (→ decisions; "superseded by" is derived),
    and the audit columns.
  - `check (supersedes_id <> id)`.
  - The chosen option has a composite FK to the decision's own options.
- **`decision_options`** (38 rows): title, `pros text[]`, `cons text[]`, `sort_order`.
- **`decision_actions`** (9 rows): description, `owner_id` → resources, `due_date`, status
  `action_status` (open, in_progress, done).
- **Link tables**, each with tenant columns and same-workspace composite FKs:

  | Table | Rows |
  |---|---|
  | `decision_risks` | 3 |
  | `decision_issues` | 0 |
  | `decision_change_requests` | 0 |
  | `decision_dependencies` | 12 |
  | `decision_benefits` | 14 |

  **There is no milestone link.**
- **`decision_status` enum**: pending, made, superseded, reversed. **There is no "deferred".**
- **Ref**: trigger `assign_ref('DEC', 'organisation')` with `unique (organisation_id, ref)`. Refs
  run **per organisation** (DEC-001 … DEC-016 across all projects), as `docs/schema.md` §1
  decided for registers that can sit at portfolio, programme or project level.

### RLS (pattern `private.my_workspace_ids(...)` / `my_editable_project_ids()`)

| Table | Select | Insert / update | Delete |
|---|---|---|---|
| decisions | workspace members | project rows: `my_editable_project_ids()`; programme or portfolio rows: workspace contributor+ | workspace manager+ |
| options, actions, links | workspace members | same as decisions | same as insert |

- **Recording a decision is just an update.** Anyone who can edit the project can set `status`,
  the chosen option, the rationale and the date.
- Nothing makes a made decision read-only. There is no "forum chair" or "decision maker" check;
  neither concept is linked to a login.
- `decision_maker_id` points at `resources`. Of the 35 demo resources only 2 have a login
  (`profile_id`). **None of the 9 decision makers on existing decisions has one.**

## 2. Assumptions

- **`assumptions`** (10 rows, ASM-001 … ASM-010; 6 open, 2 validated, 2 invalidated).
  - Columns: assumption, rationale, `validation_date`, status (open, validated, invalidated),
    notes, `owner_id`, `raised_issue_id` → issues.
  - Scope: one of the three scope columns. Ref is per organisation.
- RLS is the same pattern as decisions.
- App:
  - RAID log › Assumptions (`components/assumptions-workspace.tsx`) shows a board with editable
    validation date and status.
  - A "Validate or invalidate" list follows. Invalidate can raise an issue
    (`raiseIssueFromAssumption`).
  - **No create or delete.** The toasts say "Raise new assumptions from the project or programme
    they belong to."

## 3. What the RAID log › Decisions sub-tab renders today

- **Where:** inline JSX in `src/routes/portfolio.projects.$projectCode.tsx:400-445`. The comment
  at line 192, "Still prototype data", is stale.
- **Data:** `useGovernance()` → `loadGovernance(orgId)` (`src/services/decisions.ts:118-340`).
  - It loads every decision in the organisation with its options, actions and link ids.
  - It also loads assumptions, change requests and the forum and change-type lookups.
  - The page then filters to `projectId` with `scopedTo`, so programme and portfolio decisions
    never show on a project page.
  - **Live Supabase. No mock data, no browser storage.**
- **Each card** shows:
  - ref · title
  - a Made / Pending pill, plus "overdue" (computed in the browser, `decisions.ts:267`)
  - forum · decision maker · needed by / decided
  - context
  - "Impact on …"
  - open actions
- **Clicking a card** opens `DecisionPanel` (`components/decision-panel.tsx`), which shows:
  - context, options with pros and cons, rationale, the impact grid, actions and links
  - the evidence link as plain text
- **Writes:**
  - **Record decision** (Pending → Made: chosen option, rationale, date) and **Supersede**
    (copies the decision and its options into a new Pending decision, marks the old one
    Superseded).
  - Both need workspace contributor+ in the UI, and the project-edit RLS in the database.
  - `updateDecision` (title, forum, needed-by, status, decision maker) is used by the board on
    Governance › RAIDD.
  - **There is no create function, no delete function, and no writes to actions or link
    tables.**
- **Empty state:** "No decisions recorded for this project."

### Forums, boards and meetings

- There is no forum table and no meeting table. Forums are 5 lookup labels per organisation:
  Project Board, Programme Board, Digital Committee, Architecture Review Board, Change Advisory
  Board. These are seeded by `create_organisation`; the outsider organisation has the same 5.
- Forums have no level, chair, members, cadence or papers deadline.
- The only meeting-like tables are `phase_lessons_reviews` and their attendees.

### Committee dates and packs

- `committee_packs`: title, `meeting_date`, `collection_id` → collections, content (jsonb
  snapshot), `issued_at`, `issued_by`. 0 rows. The table isn't linked to a forum or a meeting.
- The portfolio and programme progress charts draw "committee" markers from
  `committee_packs.meeting_date`. There are none today because no pack has been issued.
- `roadmap_key_dates` has 6 rows, one titled "Digital Committee". That is a free-text key date
  on a roadmap, not a meeting.

### `milestones.report_to_committee`

- 95 milestones are flagged. The seed sets it on gates and red milestones; no UI sets or
  changes it.
- Used by:
  - Delivery › Milestones: the default view "Committee milestones" and a "Committee" tag
  - the committee pack's milestones page
  - progress chart markers, together with gates

### `status_reports.decisions_needed`

- Free text (added by `20261008191432_project_overview_schema`). **The app never writes it.**
  The status report form has Accomplished, Planned and Comments only; Comments has the
  placeholder "Add context, decisions or support required".
- 9 seeded reports carry the same sentence: "Sponsor to confirm the recovery plan and any extra
  resource it needs."
- Read by `get_project_overview` → the highlight report ("Decisions needed").
- There is no link to `decisions`.

### Business case and gate approvals

- **Business cases:**
  - Statuses: draft, submitted, approved, rejected, superseded.
  - `submit_business_case` exists (SECURITY DEFINER); the version trigger blocks status edits
    from plain client updates.
  - **There is no approve or reject.** The specified RPC `decide_business_case(version_id,
    outcome, rationale, forum_id, decision_maker_resource_id, decision_date,
    minutes_document_id?)` would record a `decisions` row and set the version's `decision_id`.
    It was never built (`docs/financials-and-business-cases.md` §2.3, roadmap item F5).
  - The one version in the database is a draft.
- **Change requests:** 6 (approved and proposed). Status is a plain editable field, with no
  forum or decision record. The `decision_change_requests` link table exists but is empty.
- **Project requests:** 6 (new, in_review, on_hold, approved, rejected). Status is a plain field.
- **Gates:**
  - Criteria are in `gate_criteria`. The checklist computes automatic checks and lets the PM
    tick manual ones, but the **ticks are page state only** and are lost on reload.
  - There is no gate approval record, approver or RPC. Gate milestones (type `gate`) exist.
- **Escalations:** no concept, table or field exists.

## 6. Decisions needed from you before D1

1. **Ref scheme.** Per project (DEC-001 for each project) means:
   - dropping `unique (organisation_id, ref)` for a per-scope one (a DROP, so a runbook block
     for you)
   - changing the trigger to project scope
   - renumbering the 16 existing decisions

   Programme and portfolio decisions would still need an organisation-level series (like change
   requests' "project or organisation" scope). The alternative is to keep organisation-wide
   refs, as risks, issues and assumptions do.
   **My recommendation: keep organisation-wide refs** so a DEC number is unique on boards and in
   packs. Switch if you prefer per project.
2. **Who records a decision while forums have no chair (D1) and decision makers have no
   logins.** The proposal:
   - The decision maker can record it if they have a login.
   - PMO and admin in the workspace can record it on behalf of the forum, like
     `decide_business_case` (decision maker and forum come from the record, not the caller).
   - The forum chair is added in D2.
   - Project editors create and edit Pending decisions but can't set Made.
3. **Deferred.** Is it a status a decision sits in (Pending → Deferred → Pending at a later
   meeting) or an outcome only? D3 counts "deferred twice", so the proposal is a status plus a
   history of deferrals (from the audit log or a deferral table in D3).
4. **Supersede of a Made decision.** Today the copy starts as Pending. The proposal keeps that:
   the new decision goes through Record decision. A "Reverse" action sets Reversed with a
   rationale, without a successor.
